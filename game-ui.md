# Game UI Design — Knowledge App

The game-skin client concept, in full. See `HANDOFF.md` for the doc map and current status; Trilium Notes is the data backend this all reads/writes against, via its ETAPI (see `AGENTS.md`; the original backend research is archived outside this repo and is SiYuan-era).

**Connectivity note**: the game UI must be built local-cache-first (layout data, task list, relevant note content cached client-side, reconciled when reachable) — self-hosted infrastructure is only reachable via local network/Tailscale, never assumed live. See `infrastructure/networking-access.md` for the full networking decision.

> **Implementation status (2026-10-20):** the world is built as designed here with these deviations: rooms are procedural pixel art (no Tiled tilemaps; zero binary assets), bookcases replace the "desk with scrolls", and an in-game **build mode** (`B`) edits how rooms look via `biblio_*` labels on room notes (themes, wall/floor decor slots, rugs, bookcase finishes) — see `README.md` and `knowledge-planning/worldediting-plan.md` Part 2. Touch/phone and Capacitor packaging are parked. A second world view, the **Yggdrasil tree** (3D in a voxel or low-poly look, folders = branches, notes = leaves, you climb it as one of nine animals in three categories), exists alongside the rooms — `T` toggles; see `README.md`, `AGENTS.md` and the guides in `wiki/`. Still **not** built from this document: texture packs, townsquare/multiple libraries, quest board, Socratic chat (Socrates is an honest placeholder), canvas/corkboard rooms, and local-cache-*first* (the tree snapshot is only an offline fallback).

## Perspective and engine

**Perspective: side-scroller, not top-down** (clarified 2026-09-24 — earlier drafts wrongly assumed top-down). This fits the metaphor better than top-down would: floors stack vertically and connect via elevators/stairs (classic Metroidvania map shape — Hollow Knight/Axiom Verge-style), bookshelves read naturally in side profile with visible spines, and Phaser's Arcade Physics is built primarily for platformer gravity/jump/ground-collision, so this is if anything the more idiomatic use of the engine. It also means the "Metroidvania hack-and-slash" game mode (Phase 3, below) isn't a bolted-on genre mismatch — it's the same perspective, same engine, same assets, just a combat-focused mode.

**Tech pick: Phaser 3** for the world (tilemap via Tiled editor, built-in input/camera/collision, touch support out of the box) with a **React/DOM overlay** for dialogue boxes, book popups, and menus — the standard "game canvas + HTML overlay" split, avoids fighting a canvas engine to render markdown or text input. Bridge via Phaser Studio's official [`template-react-ts`](https://github.com/phaserjs/template-react-ts) (Vite + a shared `EventBus` for Phaser↔React communication) rather than hand-rolling the integration. Package as a PWA for iPad/web, wrap with Capacitor for an installable Android app (thin native shell around the same web build).

**Why not Godot**: its `RichTextLabel` only does BBCode, not markdown/HTML, so it would need a native WebView bridge (GDExtension) just for reading/writing notes — the one thing that matters most. Godot's better editor/tooling wasn't worth that integration tax.

**Why not LÖVE2D**: a real, well-regarded 2D engine (Lua, lightweight — Balatro is built on it), but it has no official web export (only the unofficial, community-maintained `love.js` WASM port) and no built-in rich-text/markdown rendering or DOM — same core problem as Godot, arguably worse, for an app whose primary content is text. Ruled out for the same reason.

## Core concept

Theme: pixel-art library. Concrete mapping of the note structure onto the world, so the "game" never diverges from the real data:

- **Recursive room/door model, not fixed tiers.** Trilium note trees have no fixed depth (and a note can be cloned under several parents), so the mapping cannot assume a fixed number of tiers. Rule, applied uniformly at any depth: **any folder = one room; any subfolder = a door in that room leading to a child room.** Shelves (below) organize by tag, not by depth, so a room's shelves stay simple regardless of how many further doors it also has. **Floor/level** is reserved specifically for the first tier of folders directly under the notebook (a UX convenience matching typical top-level vault categories), with plain room/door recursion taking over below that — no special-casing needed at any deeper level.
- **Library = a notebook.** Multiple notebooks = multiple libraries; a **townsquare hub** (outside any single library) holds portals between libraries plus meta views (settings/archive/arcade) — portals are navigation, not vault content, so they don't live inside any one library.
- **Ground floor amenities** (per library): a **wisp/PC** for basic keyword search (Trilium's own full-text search via ETAPI — no new backend needed), a **receptionist** for semantic/RAG search (intelligence service retrieval endpoint, no agentic back-and-forth), and the **Socratic agent** (same intelligence service, chat endpoint, didactic persona + tools). Receptionist and Socrates are one backend capability wearing two personas — cheap to have both once either exists. Future NPC idea, not yet in scope: a **Librarian** personifying auto-link/tag suggestions (surfaces the nice-to-have with personality instead of background magic).
- **Shelf = tag.** Book spines on a shelf are notes carrying that tag; spine color = tag color, spine thickness ≈ note length.
- **Desk / pile of loose scrolls** in each room = untitled/unfiled notes (covers the "note not filed anywhere" must-have without forcing everything into the room metaphor).
- **Opening a note** = interact key → either a "book" popup (rendered markdown, page-turn style) or a flip to a terminal-style raw-markdown pane.
- **Canvas/graph notes = a corkboard room** — pins + string, drag/pan; embedding an existing note = pinning a small book icon that opens the same book popup. Keeps canvas notes as a distinct, recognizable room type instead of blending into the shelf metaphor.
- **NPCs**: Socrates in a courtyard/agora room — walking up opens a dialogue box wired to the intelligence service's chat endpoint, scoped to whatever notes are "nearby" (same room/tag) by default, whole-vault on request. Start with exactly one NPC; resist adding more until this one earns its keep.
- **Quest board**: a room/board in the **townsquare** (not inside any specific library, since it's cross-library meta content like portals) showing real tasks as "quests" — the visual front-end for the Radicale/CalDAV task data (see `scheduling-calendar.md`), not a separate to-do system. Completing a task in-game just checks off the real underlying task.
- **Doors/portals**: Archive door → graph/backlink visualization; Workshop door → settings/plugins; (later) Arcade door → generated minigames.
- **Progression currency**: keep it light — an "Insight" counter that unlocks cosmetic room decorations only, never gates features or turns note-taking into a chore-tracker. Store it as a label on a dedicated note rather than inventing new storage.

## Texture packs (modular art, swappable at runtime)

- Every visual asset is referenced in code by a **stable key** (`"character.socrates.idle"`, `"tile.bookshelf.wood"`), never a file path.
- A **pack** = a folder + `manifest.json` mapping those keys to actual files, following the same PNG+JSON contribution contract as any other community art drop.
- Phaser can load assets dynamically at runtime, so a pack picker in settings re-points the key→file mapping and reloads only the changed textures — no rebuild needed.
- One default pack ships with the app; anyone satisfying the same key contract can drop in a new one and it appears in the picker. This is the actual mechanism behind "others can contribute their own look."
- **Starting default pack (side-scroller, all CC0/commercial-safe, no attribution required):** Kenney's [Pixel Platformer](https://kenney.nl/assets/pixel-platformer) / [Platformer Characters](https://kenney.nl/assets/platformer-characters), Pixel Frog's **Pixel Adventure** (itch.io), or Ansimuz's **SunnyLand** (itch.io) — SunnyLand notably ships a ready-made Phaser project, a good head start given the chosen stack. (The Universal LPC Spritesheet raised in earlier discussion is a top-down 4-directional walk-cycle standard — wrong fit now that the perspective is confirmed side-scroller; use the platformer packs above instead, and note LPC's CC-BY-SA/GPL license carries attribution + share-alike obligations the CC0 packs above don't.)
- **A simple in-game pixel editor** (grid + palette + export, wired directly into the texture-pack manifest so painting a sprite and registering it under a key is one flow) is a nice-to-have worth building eventually — better than embedding a general external editor and bridging its output back in. Piskel (FOSS, MIT) is worth a look as UI reference, not for embedding wholesale.

## Dynamic, editable tilemap (auto-grows with folders, user-customizable)

The most substantial subsystem in the plan beyond the intelligence service itself — build the static version first, treat the auto-placement/elevator behavior as a follow-up increment once the static version is worth living in day-to-day.

- **Layout is data, not a hand-authored map — stored as custom block attributes, not a hidden folder.** Use Trilium labels via ETAPI (`POST /etapi/attributes`; names without dots, e.g. `biblio_x`, `biblio_y` — Trilium strips dots from attribute names) directly on the folder/note itself, rather than a separate JSON file or hidden directory. Labels are stored with the note, so Trilium's own sync carries the layout with zero extra config, and it travels with the note/folder if renamed or moved (attributes stick to the noteId, not the path). Texture-pack choice and other device/display preferences are the exception — those aren't "about" any note, so keep them as local, unsynced device storage instead.
- **Sync algorithm** (run on load/refresh): diff the current folder/note tree against the layout store. New folder → auto-place a new room in the next open grid cell. New note in an existing folder → auto-slot onto that room's shelf. Deleted folder → room becomes empty/archived, never auto-deleted. Anything manually repositioned is left untouched — auto-placement only fills gaps, never overrides existing layout.
- **Edit mode**: a toggle enabling drag-to-reposition (standard Phaser pointer input); on drop, write the new position back to the layout store.
- **Elevator/multi-floor scaling**: once room count crosses a threshold, new rooms start a new floor instead of sprawling infinitely, with an elevator object auto-spawned to connect floors — a simple bin-packing/overflow rule, not real procedural generation.

## Considered as a reuse base: OpenPixel-RPG — not adopted

MIT-licensed AI-generated pixel-art open-world engine ([tensor2023/OpenPixel-RPG](https://github.com/tensor2023/OpenPixel-RPG), React 19 + Phaser + Node/Express). Not a good fit despite the permissive license: its actual bulk is a real-world-photo/address-to-map generation pipeline (OpenStreetMap + Google Maps geocoding + Gemini/GPT/DeepSeek, all paid APIs) — irrelevant here since this project's map comes from folder/tag data, not a real address. The part that does overlap (Phaser+React glue) is trivial to set up from the official `template-react-ts` anyway. Stripping the irrelevant 90% would cost more than building the correctly-scoped thing directly — not adopted. One idea worth keeping from it, not the code: its NPC engine runs a **perceive-decide-act loop** for simulated characters — relevant pattern if the "living note" NPC (below) needs to wander/react rather than stand still.

## Phase 3 (cut from active roadmap, 2026-09-25 — kept as theoretical someday list)

Following the persona debate (`persona-debate.md`, archived outside this repo) — unanimous finding that effort had gone where the docs were fun to write, not where the stated priorities (capture, calendar) were — these game modes are **cut from active planning entirely**, not merely deferred. Keep them documented here for future reference only. If a low-cost architectural hook toward any of these falls out naturally during real implementation work on the core app, take it opportunistically — but don't design around them in advance or spend planning attention on them until they're actually greenlit again.

All three ideas below are cheap to build *if ever revisited* specifically because they recombine capabilities already in the plan (the RAG/chat endpoint, the room/door graph, the book-popup UI) rather than requiring new subsystems — that property still holds, it just isn't a reason to build them now.

**Debate finding worth remembering if revisited**: the Game Designer persona judged corruption ("strongest idea" below) as mechanically the weakest of the three — no tell, no fail state, no cost for missing it, resolved by a menu click — versus the "note comes alive and quizzes you" idea, which has an actual chase/catch/challenge/resolve loop. If this bucket is ever reopened, that mechanical critique should inform which idea gets built first, independent of which one sounded most interesting when originally written down.

**Hard rule, non-negotiable: no game mechanic may ever write to real note data.** This app's premise is being a trustworthy knowledge base — a mechanic that touches actual `.sy` files, even "temporarily, easily fixable," is one bug or sync-timing accident from real data loss. Every mode below is designed so this is structurally impossible, not just discouraged.

- **Metroidvania hack-and-slash defending levels/floors** — pure minigame, entirely game-state (XP/currency), no note interaction at all. Lowest risk, least connected to the actual knowledge-management value — treat as filler content, lowest priority of the three.
- **Corruption bleeding into notes** (strongest idea) — the intelligence service generates a "corrupted" variant of a passage (subtly wrong statement/planted error), stored **only in game-layer state**, never in the note itself. The book-popup overlays the fake passage on top of the real rendering at display time; the underlying note is untouched throughout. Fixing it just deletes the corruption record. Auto-trigger on notes not revisited in a while for a built-in spaced-repetition effect wearing a game skin. Cheap to build: it's the existing embedding/generation pipeline pointed at "generate a subtly wrong variant" instead of "answer a question."
- **A note comes alive and quizzes you to return** — a game-layer sprite (not the real note) spawns and paths through the existing room/door graph; catching it opens the same book-popup/dialogue system with quiz questions generated read-only from that note's content; a correct answer flips a game-state flag that "returns" it. No real data touched at any point.

**Habitica-style progression** (optional, later): doesn't conflict with anything scoped — the cosmetic-only "Insight" currency already planned is the seed of this. Could grow into a fuller stat/unlock system (decorations, NPC dialogue variants, texture packs) without forcing it now.

**The rule, clarified 2026-09-25** (resolves an apparent contradiction between "not a fan of gamifying with just stats" and "not entirely against Habitica-style progression"): the objection was never to progression itself — it's to progression that's just an abstract number disconnected from anything that matters, the way most Habitica-style systems bolt on a separate leveling layer nobody actually cares about. Progression is fine, even good, **if it's meaningful within this specific world** (unlocking a decoration in the library you actually built and use) rather than a generic stat-tracker layered on top. Keep this distinction explicit when Phase 3 progression gets designed, so it doesn't drift into the generic version by default.

## Alternative approaches (if the literal 2D world is too much)

1. **Illustrated DOM/CSS "fun" UI, no engine** — a mascot-driven, animated flat interface (Duolingo-style) instead of a walkable world. Much less effort, trivially responsive/accessible/mobile, no collision/movement system to build. Loses the literal walk-around novelty but keeps "fun, not stats-gamified."
2. **Godot (HTML5 + native Android export)** instead of Phaser — gets a real native Android build for free instead of a Capacitor wrapper, one engine for both targets. Tradeoff: GDScript/C#, and markdown/chat panels need embedded native webviews inside Godot rather than plain DOM — more integration friction for the parts that matter most (reading/chatting).
3. **Skin the graph view only** — keep everything else as plain Trilium UI, and spend the game-art budget on making the existing link map visually rich (sprite-based nodes, thematic styling) instead of a full explorable world. Smallest scope, still visually distinctive, defers the "is a walkable game world worth it" question entirely.
